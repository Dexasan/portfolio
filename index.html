Ditch

A browser-based live studio that pushes one stream to every platform simultaneously — and brings viewers back onto the screen from any of them.

Node.jsTypeScriptRTMPffmpeg WebRTCSupabaseRailwayVercel Socket.ioFastifyNext.js 14

The problem

Every live platform bans creators from streaming to competitors simultaneously. Twitch, YouTube, TikTok, Kick — pick one. Multi-streaming tools like Restream push video to multiple destinations but change nothing about the interaction model. The viewer is still passive, the audience is still split, and nobody had solved both problems simultaneously.

What I built

Multi-stream relay. A custom Node.js WebSocket server receives the H.264 stream from the browser, pipes it through ffmpeg, and fans it out via RTMP to all connected platform destinations in parallel. Because Ditch is the RTMP origin — not a relay sitting between creator and platform — cross-streaming restrictions don't apply.

Participant flow. Any viewer on any platform can click a link, grant camera access, and appear live on the creator's stream within 60 seconds — broadcast back to all platforms simultaneously via WebRTC (Agora SDK) and the canvas compositor.

Full API layer. Fastify REST API with Supabase JWT validation: auth, channels, sessions, destinations, participants. Row-level security on every table. RTMP credentials are server-side only — never returned to the browser.

Real-time infrastructure. Socket.io server handles chat aggregation from all platforms (normalized into one shape), participant signaling, and session state broadcast to all connected viewers.

The hard problem: background-tab safety

Browsers throttle requestAnimationFrame when a tab is backgrounded. A canvas compositor that relies on rAF drops to ~1fps the moment the creator switches tabs — killing the stream.

The solution uses a Web Worker with a setInterval timer (Workers are not throttled by the background tab policy) combined with the Breakout Box API to pull frames from the WebRTC track into an OffscreenCanvas. The compositor runs at stable 30fps regardless of tab visibility.

// Web Worker — not throttled when tab is backgrounded const worker = new Worker('/compositor.worker.js'); worker.postMessage({ type: 'start', fps: 30 }); // Breakout Box API — pull frames from WebRTC track const processor = new MediaStreamTrackProcessor({ track }); const reader = processor.readable.getReader();

Stream startup sequence

  • Creator clicks "Go Live" → browser opens WebSocket to relay server
  • Relay authenticates JWT, fetches RTMP credentials for all destinations
  • ffmpeg spawns with -vcodec copy -acodec aac flags — forces H.264 key frame on first packet
  • Parallel auth queries to all platform RTMP endpoints — not sequential
  • First video frame delivered to all destinations: 4–6 seconds from button click

Ditch Studio

A browser-native OBS alternative with scene switching, canvas compositing, WebRTC capture, and audio mixing — zero installation, runs entirely in a tab.

Next.jsTypeScriptCanvas API WebRTCAgora SDKWeb Audio API OffscreenCanvasWeb Workers

The problem

OBS is powerful but requires native install, GPU access, and complex scene configuration. For Ditch's use case — a viewer joining a stream, going live, then leaving — the friction is prohibitive. The tool needs to be zero-install, immediately usable, and the compositor needs to be owned by Ditch to bake participants into the RTMP output and power the ad network.

Canvas compositor

The compositor runs as a React hook (useCompositor) that manages a canvas element, draws layers in z-order on each frame tick, and exposes the canvas stream via canvas.captureStream() as a MediaStream for the relay. Each scene owns its own layer configuration — switching scenes is instant because the compositor reads the active scene's layer config on each tick.

  • Background layer: solid color or image, always drawn first
  • Screenshare layer: full-frame or PiP, z-ordered below camera
  • Camera layer: draggable Meld-style overlay, position persisted per scene
  • Participant tiles: grid layout, auto-resized by count

Background-tab safety

The browser throttles requestAnimationFrame in backgrounded tabs — an rAF-based compositor drops to ~1fps the moment the creator switches away. The solution moves the render tick into a Web Worker using setInterval (Workers run at full speed regardless of tab visibility), with frame transfer via OffscreenCanvas + the Breakout Box API (MediaStreamTrackProcessor / MediaStreamTrackGenerator).

Camera: user intent gating

Camera acquisition is gated on explicit user intent — getUserMedia is called only when the active scene has camera enabled. This prevents the browser showing a persistent "camera in use" indicator between scenes and avoids the getTracks()[0].stop() race condition that produced closed-track errors in early builds.

Controls shipped

  • FPS toggle: 30 / 60fps — changes Worker interval live without restarting the stream
  • Scene management: create, rename, delete; each scene persists its own layer state
  • Screenshare: getDisplayMedia, composited as a layer below camera
  • Draggable camera overlay: pointer capture API, snap-to-default per scene

BarcaBuzz

Built the analytics and content-growth infrastructure behind a football community that reached 100K+ followers organically — no paid acquisition.

Analytics SystemsContent Pipelines A/B TestingGrowth Engineering

The insight

Most social media growth is treated as a creative problem. That's true at the margin, but it misses the structural driver: content that grows consistently is produced by a repeatable system. BarcaBuzz started as a football fan account. It reached 100K+ because I treated it as an engineering problem — what formats convert views to follows? What cadence compounds engagement over time? What feedback loops make the next post more effective than the last?

What I built

Content pipeline. A structured system for sourcing, formatting, and scheduling content — each piece categorized by type, tracked by engagement metrics, and fed back into future decisions. The pipeline removed creative decision-making from production: the system tells you what to make next.

Analytics tracking. Platform-native analytics plus manual tracking across reach, engagement rate, save rate, and share rate. The key metric is save rate — it predicts long-tail reach better than immediate engagement.

A/B experimentation. Systematic testing of format variables: thumbnail style, caption length, hook structure, posting time, hashtag sets. Each variable isolated, tested across ≥10 posts, result fed back into the default template.

Engagement feedback loops. Comments and DMs processed as signal. Recurring questions became content. High-engagement replies tuned future hook writing.

What it taught me

Before writing a line of production code, BarcaBuzz taught me that systems beat effort. A well-designed pipeline at 60% effort outperforms a creative sprint at 100% because it compounds. The same principle applies to software — the architecture matters more than how hard you work inside it.

It also taught me that the metric you optimize for shapes the system you build. Optimizing for followers produces different content than optimizing for save rate — and save rate turns out to be the leading indicator for follower growth. Choosing the right metric is half the design problem.

RTMP Stream Tools

A Node.js CLI toolkit for probing, simulating, and debugging RTMP pipelines — built during Ditch development to test the relay without a full upstream source.

Node.jsTypeScriptffmpeg Node Media ServerCommander.js

Why it exists

Testing an RTMP relay requires a source stream. Early in Ditch development, every relay code change required a full browser session, camera permission, and a live WebRTC connection — a 2-minute manual loop. The toolkit simulates an upstream RTMP publisher so the relay can be tested in isolation: no browser, no camera, no UI. Feed it a video file or a generated test pattern, point it at the local relay endpoint, observe terminal output.

What's in the toolkit

  • sim: ffmpeg-backed RTMP stream simulator. Supports a video file source or a synthetic color-bar test pattern with timecode overlay. Configurable bitrate, resolution, and keyframe interval.
  • validate: Parses ffmpeg output configurations, checks H.264 encoding flags, validates keyframe interval and GOP size, warns on configs known to cause silent failures on specific platform ingest endpoints.
  • monitor: Polls Node Media Server statistics — active sessions, input bitrate, output destinations, reconnection events. Formatted as a live terminal dashboard.
  • probe: Uses ffprobe to inspect a live RTMP stream's codec, bitrate, resolution, and frame rate. Verifies the relay passes through stream parameters faithfully.

Usage

# Push a test stream to local relay rtmp-tools sim --url rtmp://localhost:1935/live/test --pattern bars # Validate ffmpeg config before going live rtmp-tools validate --config ./relay/ffmpeg.config.ts # Monitor relay session health live rtmp-tools monitor --host localhost --port 8000 --interval 2000 # Probe an active RTMP stream rtmp-tools probe rtmp://localhost:1935/live/test

Impact

Reduced relay iteration loop from ~2 minutes to ~10 seconds. The config validator caught three ffmpeg flag errors that would have caused silent failures on specific platform ingest endpoints. The monitor was used throughout Day 10 sustained-stream testing to verify 30fps held under tab backgrounding and that auto-reconnect triggered correctly on simulated ffmpeg exit.

Learning Projects

The breadcrumb trail of building production systems from first principles — university coursework, TypeScript experiments, and systems programming exercises from Year 1 at Tor Vergata.

TypeScriptCPython AlgorithmsSystems Programming

Engineering Sciences, Year 1

The curriculum at Tor Vergata covers mathematics (calculus, linear algebra, discrete math), physics, algorithms and data structures, and introductory systems programming in C. The coursework runs in parallel with Ditch — the university subjects provide the formal foundation, the startup provides the applied one.

The most useful intersection so far: algorithms and data structures. Understanding time and space complexity at a formal level changes how you think about infrastructure decisions. The relay's fan-out logic, the compositor's frame queue, the chat aggregator's deduplication — all better because of that grounding.

TypeScript experiments

Typed event emitter from scratch. Built before understanding how Node's EventEmitter works internally. Constraints: generic type parameters for event maps, no any, deterministic listener call order. Led to the patterns now used in Ditch's relay event system.

Promise concurrency queue. Execute at most N promises in parallel, queue the rest. The first genuinely useful abstraction I wrote. Used in the relay to cap simultaneous RTMP connection attempts to platform endpoints.

WebSocket reconnect wrapper. Exponential backoff with jitter, configurable max attempts, typed message protocol. Became the basis for auto-reconnect in useRelayStream (5 attempts, 2s base delay).

Systems programming (C)

Working in C for coursework strips away abstractions and forces explicit thinking about memory, ownership, and process boundaries. Knowing that a buffer overflow is real — not abstract — changes how you think about WebSocket message parsing in Node.

  • Process management: fork, exec, wait, signal handling
  • File I/O: standard C streams, low-level read/write syscalls
  • Memory management: malloc, realloc, free — and the bugs they produce
  • Networking: BSD sockets, TCP client/server in C

What I'm working toward

The learning projects aren't separate from the production work — they're the substrate it runs on. The goal isn't to collect languages. It's to build a mental model of systems at multiple levels of abstraction: from the OS process model to the browser event loop to the product interaction model.

Next formal area: networking — TCP/IP internals, HTTP, and eventually RTP/RTCP (the protocols under WebRTC). Understanding what Agora SDK abstracts away is the prerequisite for eventually replacing it.
